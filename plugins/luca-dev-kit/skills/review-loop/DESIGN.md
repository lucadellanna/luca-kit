# Design decisions

| Decision | Rationale |
|----------|-----------|
| OWNER/REPO fetched per-round (not cached in state file) | Each round is a separate Claude invocation via ScheduleWakeup. OWNER/REPO are fetched once per round in step B -- not in a tight inner loop. Caching in the state file adds state management complexity for negligible gain (one extra API call per round among many). |
| OWNER/REPO extracted from PR URL (not `--json repository`) | `gh pr view --json repository` is not a valid field in the gh CLI. Parsing `owner/repo` from `--json url` (always `https://github.com/{owner}/{repo}/pull/{N}`) is reliable and works in all GitHub environments including Enterprise. |
| FIX_THREADS_JSON passed via stdin (printf pipe, not env var) | Thread data is passed as `printf '%s' "$FIX_THREADS_JSON" \| python3 -c "import sys, hashlib; data = sys.stdin.read()..."`. The hash step is the only consumer and stdin is consumed exactly once, making the pipe idiomatic. Both approaches handle typical PR thread data (well under 50KB) without hitting ARG_MAX limits. |
| PushNotification instead of osascript for exit alerts | `osascript display notification` fires as a macOS system notification, which feels like a background app calling out unexpectedly. `PushNotification` is native to Claude Code, where the user already is, and requires no platform check. |
| No lockfile on `~/.claude/code-review-checklist.md` | Claude processes one task per session; true concurrent writes require multiple simultaneous Claude sessions, which is uncommon. The checklist is human-curated; a corrupted line is trivially noticed and fixed. Lockfile overhead is not justified. |
| No pre-flight Gemini installation check | Checking historical PR review activity (whether `gemini-code-assist` appeared in recent PR authors) is a proxy that fails on every first-time use: a fresh install has no historical activity. The 24-minute timeout path already covers the not-installed case with an actionable install URL. A false-positive warning that says "Gemini not found" when Gemini is installed erodes trust, so the check was removed entirely. |
| Classify and fix merged into one sub-agent (v0.2.0) | Two sequential sub-agents (classify then fix) read the same files twice, adding 30-60s per round. A single sub-agent with phased output (classify, check MANUAL/cycle, then fix) eliminates the redundant file reads and inter-agent latency. The security fence is on the sub-agent prompt, not on the separation between agents, so the untrusted-content boundary is preserved. Phase ordering guarantees cycle detection before any code is touched. |
| Review state and threads fetched in single GraphQL call (v0.2.0) | Steps B (review state via `gh pr view --json reviews`) and C (threads via `gh api graphql`) were separate API calls. A single query fetching both `reviews(last:50)` and `reviewThreads(first:100)` eliminates a network round-trip per round. |
| Checklist update inside fix sub-agent (v0.2.0) | The fix agent already knows which bug classes it fixed. Moving the checklist append into the same sub-agent saves a sequential orchestrator step (~5-10s) per round without reducing visibility: the sub-agent reports what it appended in its structured output. |
| Adaptive poll timing by diff size (v0.2.0) | Gemini response time correlates with diff size. Later loop iterations typically push small fixes (<20 lines). Polling at 90s instead of 240s for small diffs saves 2-3 min per round; for large diffs the 240s default is preserved. Subsequent follow-up polls stay at 120s regardless. |
