# Design decisions

| Decision | Rationale |
|----------|-----------|
| Plain `codex exec` instead of the `codex exec review` subcommand | `--add-dir` (needed to grant read access to `~/.claude/CLAUDE.md` and `~/.claude/rules/*.md` for the rule-adherence check) only exists on plain `codex exec --help`, not on `codex exec review --help`. Using plain exec also means our review prompt is the only instruction set in play -- no unknown built-in review template mixed in, which keeps behavior predictable and fully covered by our own empirical testing. |
| `--sandbox read-only` combined with `--add-dir "$HOME/.claude"` | Empirically verified (2026-07-22): a session started with both flags could read a file inside the added directory but a subsequent attempt to write to that same file failed with "operation not permitted". Read access for rule files does not have to trade off against the write blocklist invariant. |
| Codex computes its own diff (`git diff origin/<BASE>...HEAD`) instead of the orchestrator pasting a diff into the prompt | The review prompt requires reading every changed file in full plus its callers/callees, not just diff hunks. That requires Codex's own shell/file tools inside its sandbox; a pre-computed diff string would work against that instruction by removing the reason to explore further. |
| Session resume (`codex exec resume <thread_id>`) for round 1+, not a fresh `codex exec` each round | Requested for token economy: avoids re-reading unchanged files from scratch every round, and the sandbox/`--add-dir` grants (which `resume` does not accept as flags) carry over automatically from the round-0 session. Mitigates the obvious risk (a resumed session trusting its own prior conclusions instead of re-checking) by explicitly instructing round 1+ prompts to re-verify each prior finding against the current code rather than accepting the outcome label on faith. |
| No `ScheduleWakeup` / adaptive-delay / wakeup-prompt-template machinery (present in the archived Gemini version) | Gemini Code Assist is an async external GitHub bot that can take up to ~12 minutes to respond, so the loop had to survive being re-invoked by `ScheduleWakeup` across idle time. Codex CLI is a local synchronous subprocess: a review call either completes in the foreground (up to Bash's timeout) or is backgrounded with `run_in_background: true`, which auto-notifies on completion. There is no multi-minute *external* wait to survive, so none of that machinery has an equivalent need here. |
| No inline GitHub PR review threads, no PR comments of any kind | Explicit user requirement: no GitHub side effects beyond `git push`. Classification bookkeeping (what was FIX/REJECT/ALREADY_FIXED/MANUAL) lives entirely in the local state file and is re-fed to the resumed Codex session directly in the round N+1 prompt -- there is no GitHub-side state to keep in sync, so the entire thread-resolution GraphQL layer from the Gemini version is dropped. |
| `gh pr checks --watch` kept in EXIT CLEAN | This is a read-only CI status check, not a write/post to the PR, so it does not violate the "no GitHub side effects other than push" constraint. Kept because it gives the same "PR is actually ready" confirmation the Gemini version gave. |
| Findings identified as `F1`, `F2`, ... assigned by the orchestrator, not a Codex-provided id | The output schema has no id field (Codex findings aren't rows in an external system like GitHub review threads with a stable node ID) -- per-round positional ids are sufficient because there is no cross-system resolve call that needs a durable identifier, only cycle-detection hashing over finding content. |
| `--output-schema` + `-o <file>` instead of parsing the agent's free-text final message | Empirically verified (2026-07-22) to produce clean, directly-parseable JSON, including a nullable field (`"suggested_fix": null`) via `"type": ["string", "null"]` in the schema. Avoids brittle regex/markdown-fence scraping of free text. |
| `CODEX_BIN` resolved via `command -v` (accepted only if it yields an absolute path) before falling back to fixed install-directory candidates, never bare `codex` | Observed directly in this environment: `codex` can resolve to a shell function wrapper (`codex () { _notify command codex "$@"; }`) that fails with "command not found: _notify" before ever reaching the real binary; `command -v` for such a function returns the bare name (no `/`), so requiring an absolute-path result filters it out without extra bookkeeping. PATH is checked before the fixed candidates (matching the general CLI-resolution rule in `~/.claude/CLAUDE.md`) so a current PATH-installed binary wins over a stale one left behind in `/opt/homebrew/bin` or `/usr/local/bin`. |
| Global rule files (`~/.claude/CLAUDE.md`, `~/.claude/rules/*.md`) granted access once at round 0, not re-granted per round | `--add-dir` is not accepted by `codex exec resume` (confirmed via `--help`), because additional readable/writable directories are a session-level setting fixed at session start. Granting it once at round 0 and resuming the same session for all later rounds is both correct and the only option -- there is no per-round equivalent. |
| `last_classification_table` persisted to the state file, not kept only in conversation memory | The round N+1 prompt's `<PRIOR_FINDINGS>` block needs the previous round's full classification table. If the loop is re-entered from `.claude/cache/review-loop-state.json` after an interruption (fresh Claude session, no conversation history), only what's on disk is available -- so the FIXED-state update persists the table verbatim rather than relying on it staying in context. |
| Setup checks Codex auth via `codex doctor` output, not just binary presence | A `command -v codex` check alone passes for an installed-but-not-logged-in Codex, which would let `open-pr` create and push a PR before `review-loop` fails on auth partway through. Grepping `codex doctor` output for "auth is configured" catches that case at setup time instead of mid-loop. |
| Cross-repo call-site check gated by `git diff --diff-filter=MR` (structural), not a line-count threshold | Observed directly (2026-07-22): a round-0 review of a 17-file/1071-line diff consumed ~3.4M cumulative input tokens (94% cache-served, but still the dominant cost driver in dogfooding this skill). An earlier version of this gate used a `<20 lines` cutoff, but line count is a poor proxy for the actual question ("did anything pre-existing change shape") -- it wrongly skips a 15-line rename of a widely-used function and wrongly includes a 500-line brand-new file. `--diff-filter=MR --name-only` (modified-in-place or renamed files only, excluding pure additions/deletions) combined with `-w --ignore-blank-lines` (excluding whitespace-only "modifications") is a free, deterministic, structural signal computed by the orchestrator with a single git command -- no LLM call needed for the gate itself. Empirically verified (2026-07-22) against this repo's own migration commit, which mixed modifications, pure additions, and one file rename: the filter correctly kept only the modified/renamed set. The precomputed file list is handed to Codex directly in the prompt rather than asking it to re-derive which files were modified vs. added. |
| Round 1+ reviews only the incremental diff (`last_reviewed_commit_oid..HEAD`), not the full PR diff against base | Observed directly (2026-07-22): telling Codex to recompute `git diff origin/<BASE>...HEAD` every round (the full, ever-growing cumulative diff) meant round 1's own incremental turn cost more *fresh* (non-cached) tokens than round 0's entire review, despite reviewing what was framed as a much smaller change. Round 0 already covers everything up to the commit it reviewed; re-running the full 14-category checklist against the full cumulative diff on every later round is redundant by construction in a resumed session, not merely expensive in practice. `last_reviewed_commit_oid` (the commit `git rev-parse HEAD` returned right before this round's Codex call) is persisted to the state file specifically so the next round has an exact incremental range, rather than the `HEAD~<N>` guess this replaced (see the next row). |
| `HEAD~<N>` (guessed commit count) replaced with `last_reviewed_commit_oid..HEAD` (recorded commit) for round 1+'s diff range | The `HEAD~<N>, normally N=1` framing this replaced was already known to be wrong in practice: dogfooding this skill on its own PR needed 5 commits between round 0 and round 1 (a fix commit plus follow-up commits from continued design iteration and an auto-committing version-bump/index script), not the assumed 1. Recording the actual reviewed commit removes the guess entirely and is exact regardless of how many commits land in a round. |
| Two qualification bars adapted from Conductor's own Codex review-agent prompt: "not a pre-existing issue" and "must identify the provably affected code, not speculate" | Read directly (2026-07-22, user-supplied). Conductor's prompt for PR review (a different, general-purpose agent, not this skill) uses a short, crisp bug-qualification checklist rather than an exhaustive category list, including "the bug was introduced in the commit (pre-existing bugs should not be flagged)" and "it is not enough to speculate that a change may disrupt another part of the codebase... one must identify the other parts of the code that are provably affected." Both directly target scope creep this skill had already hit empirically: the first bounds the correctness checklist to the diff, not a repo audit; the second was folded into the cross-repo call-site check specifically, turning "grep and report if plausible" into "grep and report only if proven" -- a stronger anti-speculation bar than the existing "concrete failure scenario" requirement gave that one check on its own. |
