# Design decisions

| Decision | Rationale | Alternatives considered | Status |
|---|---|---|---|
| Checklist derivation runs in main agent, not a subagent | The main agent reads the file once and produces the checklist; the subagent receives only the path and the checklist, never the file content. When the file is already in main context (typical), derivation is essentially free. When it isn't, the main-agent read is the only read either way; a derivation subagent would just duplicate it. | (a) Dedicated derivation subagent. Rejected: doubles file reads with no isolation benefit. (b) Always require user-supplied checklist. Rejected: lowers usefulness for ad-hoc review. | Locked. |
| Files near the ~1000-line limit pollute main context for the session | The main agent must load the file to derive the checklist. For very large files this is the design's main cost. The scope limit keeps it bounded. | (a) Page the file and derive incrementally. Rejected: complexity not worth it at this scope. (b) Push derivation into a subagent only for large files. Rejected: branching the design on size is fragile. | Locked. |
| Single file per invocation; no directory or diff mode | The two-phase contract works because the main agent produces a *specific* checklist for one file. Across files, items become generic and the skill collapses into `triple-review`. | (a) Multi-file with one checklist per file. Rejected: dilutes the specificity guarantee. (b) Directory walk. Rejected: out of scope; use `triple-review`. | Locked. |
| Subagent output uses a structural `FINDINGS:` marker, not prose suppression | LLMs strongly want to add preambles and OK lines; prose-level "do not say X" instructions are brittle and fail on paraphrase. A structural marker the main agent can parse is enforceable regardless of whether the subagent also emits chatty text. Anything before the marker is discarded. | (a) String-equality check on `"no bugs found"`. Rejected: fails on paraphrase. (b) Trust the subagent to omit OK lines per prose instruction. Rejected: empirically unreliable. | Locked. |
| Re-spawn budget capped at 1 retry | Without a cap, a misbehaving subagent burns cost in a loop. One retry catches most one-off contract violations; a persistent violation indicates a real problem the user should see. | (a) Unbounded re-spawn. Rejected: cost runaway. (b) Zero retries. Rejected: a single re-spawn empirically resolves most contract violations. | Locked. |
| Mandatory Grep uniqueness pre-flight before each Edit | Subagent reports a line number, but Edit uses string matching. A non-unique `old_string` silently applies to the wrong occurrence; a zero-match `old_string` (subagent paraphrased rather than quoted) crashes the Edit with no recovery. Pre-flight catches both deterministically. | (a) Trust the executor's judgment. Rejected: "use your judgment" is exactly the failure mode this skill is designed around. (b) Always pass the file's full text as `old_string`. Rejected: blows up token cost. | Locked. |
| Adjacent-edit conflicts surface to user rather than auto-merge | When two approved findings target the same or adjacent lines, "merge them automatically" is not implementable as an unambiguous LLM instruction. Asking the user is one extra click but produces a correct outcome; auto-merge produces silent wrong outcomes. | (a) Merge automatically by composing both new_strings. Rejected: unimplementable instruction; LLM judgment is the failure mode. (b) Apply both sequentially and let the second Edit fail. Rejected: silent failure on the second fix. | Locked. |
| Auto-derive checklist when none is supplied; do not prompt "derive or supply" | Typical invocation is `/targeted-review <file>`; prompting "derive or supply your own?" adds friction for the most common path. Users who want to supply a checklist already know to pass one inline or by path; Step 1 branching accommodates both. | (a) Always ask "derive or supply?". Rejected: friction in the common path. (b) Default to ask, fast-path on a flag. Rejected: skill doesn't take flags; complicates the contract. | Locked. |
| Ships standalone today; candidate to fold into `triple-review` later | Standalone first lets the skill iterate without affecting `triple-review`'s contract with `open-pr`. User has empirically confirmed it catches bugs `triple-review` misses. | (a) Add as fourth lens to `triple-review` immediately. Rejected: per-file checklist derivation does not fit `triple-review`'s parallel-on-diff model. (b) Skip standalone, integrate later directly. Rejected: no iteration loop. | Open. Concrete trigger to revisit: after 5 to 10 real uses, does per-file derivation latency/tokens justify integration, or is `triple-review`-first still preferred? |
| Execution subagent uses Sonnet, not Opus | Checklist is pre-derived; subagent only executes. Sonnet is the cost-quality balance for bounded execution. | (a) Opus. Rejected: marginal accuracy gain not justified. (b) Haiku. Rejected: review tasks benefit from Sonnet's reasoning depth. | Open: revisit if quality issues observed. |
| Haiku scorer in Self-reflection per plugin standard | Matches `create-skill` and other meta-skills. | None considered. | Locked. |
