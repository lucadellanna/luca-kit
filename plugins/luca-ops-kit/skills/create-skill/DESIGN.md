# Design decisions

| Decision | Rationale |
|----------|-----------|
| Three mandatory baseline criteria (conciseness, runtime efficiency, simplicity) plus 1–3 ad-hoc, total ≤ 6, MECE-constrained | The baselines are anti-overengineering checks; making them optional invites the same bloat this skill is designed to prevent. The cap keeps scoring cheap. The MECE constraint prevents double-counting of the same flaw across criteria. |
| Criteria persist as `REQUIREMENTS.md` in the skill folder | `audit-skill` can read `REQUIREMENTS.md` to score against the bar agreed at creation time, instead of renegotiating criteria with the user at audit time. Persisting the contract closes the loop between producer and checker. (The `audit-skill` side of this integration is a separate PR.) |
| Runtime-efficiency anti-patterns live in `${CLAUDE_PLUGIN_ROOT}/checklists/runtime-efficiency.md`, referenced from REQUIREMENTS.md | Single source of truth. Inlining the list in three places (SKILL.md Step 3 table, Step 6 template, every REQUIREMENTS.md instance) would drift over time. The checklist updates independently; references stay short. |
| Plugin-internal references in markdown content use `${CLAUDE_PLUGIN_ROOT}`, not repo-relative paths | Repo-relative paths like `plugins/luca-ops-kit/...` only resolve in the source repo. After `claude plugin install`, the plugin moves to the cache (`~/.claude/plugins/cache/luca-ops-kit/luca-ops-kit/<version>/`) and repo-relative paths break. The `${CLAUDE_PLUGIN_ROOT}` token resolves to the plugin's actual root at consumer runtime. |
| `audit-skill` is the terminal step | `audit-skill` is purpose-built to score skills; embedding a second scoring loop inline duplicates its work. Putting it last avoids the `pipeline-pause-after-sub-skill` error class: any parent step running after a multi-turn child is unreliable. |
| Doc-sync (Step 7) runs before `audit-skill` (Step 8) | Reverses the earlier ordering. The pipeline-pause risk after `audit-skill` outweighs the risk of registering a name the audit might still rename. Renames are rare and recoverable; a forgotten doc-sync is silent and common. |
| Step 2 overlap check uses inline Bash `grep`, not the `luca-kit:list-skills` skill | Calling `luca-kit:list-skills` from inside `create-skill` would invoke a sub-skill mid-pipeline (`pipeline-pause-after-sub-skill` risk) and reload its ~80-line inline Python every call. A 1-line `grep` over project-local SKILL.md description fields is sufficient for keyword matching. Will migrate to a shared script when `list-skills` extracts its Python (separate PR). |
| Step 2 scans `plugins/*/skills/*/SKILL.md` and `skills/*/SKILL.md` (project-local), not global skills | The MVP covers what Step 6 writes (`skills/<name>/`) plus plugin-resident skills in the same repo. Global skills (`~/.claude/skills/`, plugin cache) are out of scope: duplicates there are visible at slash-command time and rarely overlap with project-specific skills. Scope can be expanded if real duplicate incidents accumulate. |
| Terminal `audit-skill` handoff is exempt from the "approval before sub-skills" safety bar | `audit-skill` is a read-only quality check; it scores but does not modify state. Requiring a gate would add friction at the end of a workflow when the user is already done. The REQUIREMENTS.md safety bullet is scoped to file writes and doc appends, which are the actual high-stakes actions. |
| `work-context.md` is read silently in Step 1; qmd is queried only if its marker exists | Both are opportunistic. If present, they sharpen the persona, tone, and domain context without nagging the user mid-flow to set them up. If absent, the flow proceeds with elicitation as fallback. |
| Code-review pass (Step 5) is conditional | The correctness checklist only matters when the generated skill emits structured data, runs executable code, or coordinates multi-agent flows. Running it universally pays the cost on every creation for occasional benefit. |
| No inline scoring loop on the SKILL.md draft | `audit-skill` is the quality gate. Pre-audit scoring against user-confirmed criteria duplicates audit work and inflates context with iteration rounds. The user inspects the draft directly before saving. |
| No `## Self-reflection` section on this skill | Self-reflection is meant for skills producing durable artifacts the user inspects. `create-skill`'s output is a generated skill that has its own self-reflection and is then audited by `audit-skill`. A trailing Haiku scoring pass here would be a fourth gate on the same artifact. |
| No plan mode for blueprint approval | Plain show-and-confirm at the end of Step 4 is sufficient: Step 4 writes nothing, so the harness gate adds no real protection. |
| Two extra questions in Step 1 (persona, trigger) | Who uses the skill determines tone; the trigger shapes the entry point of the generated skill. Both are lost if not captured before drafting because the user rarely volunteers them unprompted. Persona is skipped when `work-context.md` already covers it. |
| Step 7 appends to existing sections only, never creates one | If neither README nor CLAUDE.md has a skills section, the project hasn't opted into that convention; imposing structure would be overreach. |
| Design decisions stored in `DESIGN.md`, quality requirements stored in `REQUIREMENTS.md`, both separate from `SKILL.md` | `SKILL.md` is loaded on every execution; the other two are read only by audits and reviews. Separation prevents audit rationale and quality contracts from inflating runtime token cost, which compounds as rationale accumulates. |
| `create-skill`'s own REQUIREMENTS.md uses 3 ad-hoc criteria (Clarity, Completeness, Safety), reaching the documented cap of 6 total | The cap "≤ 6 total, 1–3 ad-hoc" permits this. All three are MECE with the baseline (different audiences and dimensions). Future additions would require dropping one to stay within the cap. |
| `create-skill` has no top-level `## Self-reflection` section despite producing durable artifacts | Permitted by the widened exception in plugin CLAUDE.md: the produced skill is quality-gated by `audit-skill` (Step 8), which is a dedicated downstream gate. A trailing self-reflection here would be a duplicate scoring pass on the same artifact. The exception applies cleanly. |
