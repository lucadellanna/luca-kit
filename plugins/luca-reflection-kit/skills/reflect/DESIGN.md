# Design decisions

| Decision | Rationale |
|----------|-----------|
| Two specialist sub-agents instead of one prompt | Splits "improvements to how Claude operates" from "patterns in how the user interacts with Claude". One prompt blended the two and produced weaker findings on both axes. Reviewers run in parallel (single message, two `Agent` calls). |
| Raw verbatim digest, no event ledger | An earlier draft compressed turns into a numbered "event ledger". Two problems: (1) the orchestrator's selection of which events to include encoded its own blind spots into the reviewers' inputs; (2) once you also send the transcript (per the original spec), the ledger is redundant. Sending raw turns removes the selection step entirely. Tool outputs are truncated (5+5 lines) to bound digest size without losing structural signal. |
| Auto-apply gated to `.claude/memory/MEMORY.md` only | The user asked for clear wins to be applied without confirmation. The gate is intentionally narrow: target=project memory, confidence=high, ≤2 lines, not duplicate. Anything touching a skill, a CLAUDE.md rule, or another plugin's files always asks. Auto-applying memory is reversible by editing one file; auto-applying skill or rule edits is not. |
| MEMORY.md content sent to both reviewers | Lets reviewers dedupe at the source rather than having the orchestrator strip duplicates after the fact. Avoids wasting reviewer tokens on suggestions already covered. |
| Reviewers cap findings at 10 each, orchestrator caps AskUserQuestion at 8 | 15+ checkboxes is unusable. The Top-3 actions and Auto-applied sections still reflect everything; the multi-select only governs interactive choice. Remaining items appear in "Logged only". |
| Coaching language is banned | "Make the user more effective" is a false promise. The user-flow reviewer surfaces observations, never advises. The skill's external description avoids "effectiveness" / "should" / "improve your workflow" framing. |
| Opt-in for session notes moved out of Step 0 | Previous Step 0 mixed length check with an opt-in nag, which broke the plugin's "lightweight, never block" principle. The setup command is now the only place that asks. Step 7's logging bash silently checks the marker and exits when absent. |
| Free-form reviewer output, no strict JSON | The orchestrator is an LLM, not a parser. Strict JSON would add brittleness without a real upside. The field names in the agent files (`evidence:`, `confidence:`, `disposition:`) are stable enough for LLM-to-LLM handoff. |
| Single-reviewer failure surfaces a warning, never silent | If only one reviewer returns findings, the report header notes which domain was not reviewed. Proceeding silently would mislead the user about coverage. |
| Trivial logging format unchanged (date + finding strings) | Same rationale as v0.4: trivial format is parseable by `/dream`; richer data is `/dream`'s concern at consumption time. |
| Digest stays on the user's machine | Sub-agents run inside the same Claude Code session as the orchestrator. The digest is never sent to a wider audience than the orchestrator already received. This is a privacy boundary worth stating: tool outputs in the digest may contain secrets, but they do not leave the user's session. |
| Cap at 5 substantive exchanges before /reflect is meaningful | Below that, signal is too thin and findings devolve into filler. Length check is unchanged from v0.4. |
| Reviewer quality floor: recurrence-or-generalisation + two-whys + mechanism-not-instance | First live run on a real session surfaced many low-value findings: single-instance observations, re-statements of user requirements the skill already encodes, surface symptoms without naming the underlying mechanism. The quality floor lives in the reviewer mandates so the reviewer self-filters before emitting. Two-whys is the lightweight version of five-whys: enough depth to push past the instance, not enough overhead to bloat the prompt. |
| Orchestrator-level source-tree dedup in Step 3 | The reviewers cannot see the source files; they see only the digest. Findings that re-state behavior already encoded in the skill or agent files being edited in this session must be filtered by the orchestrator, which can Read those files. This is the context filter the reviewer is structurally unable to apply. |
| AskUserQuestion cap is 4, not 8 | Discovered during the first live run on this very session: AskUserQuestion has a hard 4-option limit (recorded in project memory). Earlier draft said 8; corrected in v0.5.1. |
| Pure-reasoning agents use `tools: []` | Omitting `tools:` grants access to every tool, which loads each tool's definition into the agent's system context and inflates token cost. Both reviewers receive everything they need in the orchestrator's prompt; they never call tools. |
| Full rule corpus passed to reviewers in Step 1b | Run 2 of /reflect on this very session showed the literal-duplicate gate let four functionally-duplicate proposals through (e.g., a reviewer proposed encoding a rule that was already covered by the broader global "Anchored-defense" rule). Passing the global + project + plugin CLAUDE.md content into the reviewer prompt lets the reviewer self-filter at the source, not as orchestrator post-hoc cleanup. Token cost is real (~1.5K per reviewer × 2) but /reflect runs rarely and low-value findings cost more than tokens. |
| Skills + commands index passed to reviewers in Step 1c | The user-correctable miss in run 1 was Claude proposing `agents/` inside a skill folder when the `plugin-dev:plugin-structure` skill would have given the right answer. The reviewer can only suggest "invoke skill X" if it knows X exists. The index covers project, global, and all installed plugin skills + commands. |
| "Value-adding" test in quality floor | The user's challenge ("will behavior be more correct next time without this entry?") is the cleanest test for whether a finding is value-adding. The recurrence-and-delta pairing (will the failure recur? does the fix change behavior beyond existing rules?) eliminates a class of low-signal findings that describe a problem already solved elsewhere. |
| "Prefer invoke existing over encode new" rule for reviewers | When an existing skill or command addresses the observed pattern, proposing to invoke it next time is a stronger fix than adding a memory note. The note relies on Claude reading it; invoking the skill relies on the harness routing, which is more reliable. |
| Step 3 source-tree dedup downgraded to fallback | After A+B (rule corpus + skills index in reviewer prompt), reviewers self-filter functional duplicates. The orchestrator's source-tree dedup remains as defense in depth for files the reviewer can't see (e.g., a skill file edited mid-session whose new content isn't in the digest). |
| Asymmetric reviewer outputs (v0.5.3): claude-flow → findings (actionable, gated); user-flow → observations (informational, for the user) | Run 3 surfaced a deeper design error: user-flow-reviewer was producing memory-edit findings under the guise of "user requirements", but the user's spec was always "what should the user know about their own working style". The fix: user-flow output stops proposing edits; claude-flow owns all memory-edit findings, including "user has restated X N times; memorialise for Claude". |
| User-flow output is recommendations, not observations (v0.5.4) | After v0.5.3 produced informational-only observations, a fourth user correction made it clear that the original spec was "what should the user do differently next time", which is forward-looking recommendations, not retrospective observations. The previous v0.5.3 schema (pattern + significance + direction) produced "keep doing what you're doing" outputs because the direction field couldn't carry a concrete recommendation. The v0.5.4 schema (evidence + pattern + recommendation + rationale) forces every output to name a concrete forward-looking opportunity. |
| Recommendation schema for user-flow | The user-flow reviewer outputs use evidence + pattern + recommendation + rationale. No target file (it doesn't propose edits). No disposition (it doesn't go through the gate). Effective patterns the user already employs are NOT recommendations unless a concrete refinement is worth considering; the reviewer's quality floor explicitly drops "continue doing X" entries. |
| Automatable vs user-only classification (v0.5.5) | Run 4's recommendations exposed that most "user-side" recommendations were actually Claude-side rules in disguise: "invoke /find-skills when starting work in a new domain" can be a CLAUDE.md trigger, not a user behavior change. The classification routes automatable items into the claude-flow processing pipeline (gate, ask, apply) and reserves user-flow output for the residue: things only the user can decide (when to invoke /reflect on their own cadence, how to scope their own challenges). This is the same mandate-target distinction one level deeper. |
| Hint(s) rendering with plain language | User-only recommendations render as a "Hint(s):" bullet list, recommendation in normal text + rationale in italic, max 3 (1-2 acceptable). Plain language is required: "remember preferences" not "memorialise"; "challenge specific parts" not "scope re-derivation". The user is technical but does not want to parse academic prose. |
